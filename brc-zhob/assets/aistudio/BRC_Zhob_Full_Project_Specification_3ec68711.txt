# PROJECT BLUEPRINT
## Balochistan Residential College Zhob — Integrated College Website & Management System

**Project type:** Responsive public website + admissions + role-based Learning/College Management System (LMS/CMS)

**Confirmed owner decisions**
- Technology target: XAMPP (Apache), PHP, MySQL/MariaDB.
- Delivery target: develop and test locally first; prepare for online hosting afterwards.
- Public homepage is visible to everyone without login.
- Login is optional; authentication is required only for private portals and protected actions.
- Account roles: Administrator, Teacher, Cadet/Student, Parent. Alumni registration is public and subject to admin approval; alumni portal/directory features can be enabled by policy.
- Cadet admissions must support boys and girls. Do not assume separate campus/hostel policy beyond what the college confirms.
- Website language: English for initial release; structure should allow later Urdu localization without redesign.
- Online admission applications are required.
- Priority: build the integrated system, not disconnected static mockups.

## Product goals
1. Present BRC Zhob professionally to visitors and prospective applicants.
2. Allow applicants to submit admissions online and track application status.
3. Give authorized administrators a secure central control panel.
4. Give teachers only their assigned classes and authorized academic tools.
5. Give cadets their own academic/hostel/fee information.
6. Give parents only the records of children linked and verified to their accounts.
7. Maintain alumni registration and review.
8. Use one normalized database as the source of truth.
9. Produce printable/downloadable official documents where authorized.
10. Support local XAMPP deployment first and an HTTPS production deployment later.

## Primary navigation model
### Public website (no login required)
Home | About Us | Admissions | Academics | Faculty & Staff | Hostel Life | Results | Gallery | Notices | Contact Us | Alumni Registration | Login

“Login” must not block public browsing. The public menu and footer remain available to visitors and signed-in users. A signed-in user can navigate back to public pages.

### Private portal landing after login
- Admin → `/admin/dashboard`
- Teacher → `/teacher/dashboard`
- Cadet → `/cadet/dashboard`
- Parent → `/parent/dashboard`

Server-side authorization must enforce the role on every protected route. Hiding a menu item is not an authorization check.

## Brand and design direction
- Primary: deep BRC maroon/burgundy.
- Secondary: restrained premium gold.
- Surfaces: warm cream, ivory and white.
- Typography: readable sans-serif for UI; restrained serif for large editorial headings if it matches references.
- Visual treatment: premium, reduced-transparency glassmorphism. Glass panels must remain substantially opaque enough for comfortable reading; no excessive blur, low contrast or translucent text overlays.
- Official logo: use only the supplied original logo file. Keep its artwork and colors unchanged.
- Watermark: use a faint, low-contrast version of the official logo in selected hero/background/card surfaces; never use it behind dense text where it harms legibility.
- Icons: use one consistent icon family (Bootstrap Icons or Font Awesome Free); no emoji as primary interface icons.
- Cards: measured radii, restrained gold edge accents, subtle shadows, clear state colors.
- Use the generated previews as visual guides for composition, not as literal data sources or screenshots to embed in the live website.
- Responsive breakpoints: wide desktop 1440px, laptop 1024px, tablet 768px, mobile 390px and 360px. No horizontal overflow.

## Operating assumptions
- All operational records belong to the institution and are editable by authorized roles.
- Every user must have a unique account. Initial admin setup must be secure; do not ship a known default password.
- Admission, alumni and contact forms are public; protect them with CSRF, validation, rate limits and spam controls.
- All student records, marks, attendance, payments and uploaded documents are private by default.
- Database backups and private documents must not be directly accessible through public URLs.

# PROJECT MECHANISM — HOW THE SYSTEM WORKS

## 1. Public visitor and homepage
1. Visitor opens `/` and immediately sees the public homepage; login is optional.
2. Public pages load published data from the database (homepage settings, notices, gallery albums, programs and faculty profiles).
3. Unpublished content and private records never appear publicly.
4. Login opens the dedicated sign-in screen; public navigation remains accessible.

## 2. Login and role routing
1. User submits username/email and password over HTTPS in production.
2. Server validates input, rate-limits attempts and verifies password hash.
3. Server regenerates the session ID, stores the authenticated user ID and role/permission context, and records last login.
4. Server redirects by database role: Admin → `/admin/dashboard`; Teacher → `/teacher/dashboard`; Cadet → `/cadet/dashboard`; Parent → `/parent/dashboard`.
5. Every subsequent protected request rechecks authentication, active status, role permission and record ownership.
6. Logout invalidates the session server-side. Password reset uses single-use, expiring tokens.

## 3. Online admission lifecycle
1. Guest opens Apply Now; no existing cadet login is required.
2. Applicant moves through a multi-step wizard. Preserve the reference stepper: Personal Info → Academic Info → Contact → Fee.
3. Use the exact visible fields from the supplied reference images for Academic Info and Fee. Personal/Contact fields not present in those references must be configured only after BRC confirms the official field list; do not invent extra mandatory fields.
4. Save a draft in a short-lived server session or persistent application draft keyed by a secure random token. Validate every step server-side.
5. Applicant uploads documents using allowlisted MIME types, extension/signature checks, size limits and randomized filenames. Store files outside the public web root.
6. On submit, generate a non-sequential application reference, store status `SUBMITTED`, and write status history.
7. Applicant gets a confirmation page and secure tracking instructions. Email/SMS notifications are optional integrations and must not be faked.
8. Admin reviews, requests correction if configured, verifies fee deposit manually, then approves/rejects with reason and audit log.
9. Only after approval does an authorized admin convert the application to a cadet record and create/activate account. Prevent duplicate cadet records.

### Admission fields supplied by the user screenshots
**Academic Information — use labels as close as practical to the reference:**
- Name of candidate (according to school record)
- Father's Name (according to school record)
- Class in which studying
- Medium of Instruction
- Date of Birth according to school record (in figures)
- Date of Birth (in words)
- Performance rated as % in previous exam
- Expected annual examination class
- Expected “securing more than % marks” value
- Name of School in which studying
- Warning: “Cutting, omission and erasing in Date of Birth is strictly prohibited and the same leads to disqualification.” (confirm exact official wording before public launch)

**Fee Payment Details:**
- Deposit Slip No
- Date of Deposit
- Bank Name & Branch
- Account No
- Amount (PKR)
- Attach Deposit Slip (PDF/JPG, maximum 2 MB)
- Non-refundable fee warning; actual bank details, fee amount and dates must be supplied by BRC, not invented.

## 4. Alumni registration lifecycle
1. Public user opens Alumni Registration.
2. Form collects the exact fields shown in the source alumni screenshot (see `CONTENT_AND_FIELD_SOURCE_OF_TRUTH.md`).
3. User submits; status becomes `PENDING_REVIEW`; acknowledgement is shown.
4. Admin checks duplicate Kit No / Entry No / email, reviews record and approves or rejects.
5. Approved alumni can appear in a public directory only if the user consented and Admin enables publication. Sensitive fields (CNIC, phone, address, DOB) are never public.

## 5. Teacher academic workflow
1. Admin creates academic year, class, section, subjects, teacher accounts and teacher-class/subject assignments.
2. Teacher signs in and sees only assigned classes and tasks.
3. Teacher selects class/date and records attendance. Prevent duplicate attendance for the same cadet, class and session; allow correction with audit history.
4. Teacher creates assignments and due dates; cadets submit allowed file types.
5. Teacher grades submissions and gives feedback; cadet and linked parent can read released grades.
6. For exams, Admin creates exam schedule and assigns duties/halls; teachers see assigned duties only.
7. Teacher enters marks only for assigned subjects; marks are validated and submitted for approval/publishing according to Admin workflow.

## 6. Cadet workflow
- Cadet dashboard summarizes own timetable, pending assignments, attendance, latest published results, notices and fee status.
- Cadet can submit assignments and see teacher feedback.
- Cadet cannot edit marks, attendance, fees or hostel allocations.
- Only the cadet's own records are queried and displayed.

## 7. Parent workflow
- Admin verifies guardian relationship and links parent account to one or more cadets.
- Parent dashboard selects an authorized child; all pages filter by the verified parent-child link.
- Parent sees attendance, published results, invoice/payment status, leave requests, approved hostel details and communication from assigned teacher.
- Parent cannot edit official marks or attendance.

## 8. Admin management workflow
- Admin CRUD for cadets, guardians, teachers, departments, classes, sections, subjects, academic years, timetables, hostels, rooms, fees, examinations, notices, pages and gallery.
- Dangerous actions require confirmation and audit log; destructive actions should prefer archive/soft-delete where records have financial/academic history.
- Admin dashboard metrics are computed from database queries; never hardcode sample mockup numbers.
- Reports use filters, pagination and permission checks; exports must not expose private data to unauthorized roles.

## 9. Results publishing
- Exam is created with academic year, classes, subject rows, schedule and status.
- Authorized teacher enters subject marks; validation checks maximum marks, numeric range and required entries.
- Admin reviews/locks/publishes results.
- Only published results become visible to cadet/parent/public search. Public lookup should require sufficient identifiers and return the minimum approved information. Add anti-enumeration/rate-limit protections.
- PDF report card includes verified institution branding, candidate name/roll number/class, exam, subject marks, totals, grades, issue date and verification reference.

## 10. Fees and manual deposit verification
- Admin configures fee heads and invoices; do not hardcode fee values from mockups.
- Applicant or parent submits payment/deposit reference and slip upload.
- Status begins `PENDING_VERIFICATION`; authorized finance admin verifies against real bank evidence and records who/when/decision.
- Do not mark payment paid automatically because a file was uploaded.
- Future payment gateway integration is a separate project requiring real provider credentials.

## 11. Notices, gallery and CMS
- Admin creates/edits/archives notices with category, publish date, expiry, audience and optional attachments.
- Public users see only published public notices; teacher/cadet/parent notices can be audience-restricted.
- Gallery manager creates albums, uploads optimized images, captions and alt text; photos are served from safe paths.
- Public pages and homepage content are edited through a permission-gated CMS; never allow arbitrary PHP/HTML execution from CMS fields.

## 12. Backups and online hosting
- Local data and online data are separate database instances; do not silently sync/overwrite.
- Backup process creates dated database and uploads backups outside public web root, records status and allows authorized restore after confirmation.
- Production uses HTTPS, secure secrets in server environment, database user with least privileges, disabled setup route, debug off and restricted backups/uploads.

# ROLES, PERMISSIONS AND DATA VISIBILITY

## Roles
- **Guest:** browse public pages; submit admission/alumni/contact forms; track own application only with application reference plus secure token/verification.
- **Admin:** manage the whole platform according to assigned permission set. A Super Admin role can assign roles and system permissions. Sensitive actions are audited.
- **Teacher:** access only assigned classes, students, timetable, attendance, assignments, exam duties and authorized result entry. Teachers cannot alter fee settings, user roles or another teacher's assignments unless explicitly granted.
- **Cadet:** access own profile, class/timetable, assignments, own attendance, published results, own fee status and authorized hostel information.
- **Parent:** access only linked/verified child or children. Parent cannot view any other cadet's data.
- **Alumni applicant/member:** public applicant submits registration; after approval an alumni record/account/directory entry may be enabled according to BRC policy.

## Permission matrix (summary)
| Feature | Guest | Admin | Teacher | Cadet | Parent |
|---|---:|---:|---:|---:|---:|
| View public pages | Yes | Yes | Yes | Yes | Yes |
| Apply for admission | Yes | Admin can enter/review | No | Existing cadet should not duplicate | No |
| Review/approve admissions | No | Yes | No | No | No |
| Manage users/roles | No | Yes, permission-gated | No | No | No |
| View all cadets | No | Permission-gated | Assigned only | Own only | Linked child only |
| Mark attendance | No | Yes/override, audited | Assigned classes | No | No |
| View own attendance | No | Yes | Assigned class | Own | Linked child |
| Enter marks | No | Yes/override, audited | Assigned subject/class | No | No |
| View published results | Published public subset only | Yes | Assigned classes | Own | Linked child |
| Manage fees/payments | No | Yes | No | Own read-only | Linked child read-only |
| Hostel records | Public summary only | Yes | Only explicitly granted notes | Own approved info | Linked child approved info |
| Publish notices | No | Yes | Optional permission | No | No |
| Manage gallery/pages | No | Yes | No | No | No |

## Enforcement requirements
- Use RBAC middleware and resource-level ownership checks on the server.
- Never rely on a hidden link/button as security.
- Every query for cadet/parent/teacher data must include the current user's allowed relationship/assignment constraints.
- Log administrator overrides, result edits, fee verification, admission decisions, account creation/deactivation and role/permission changes.
- Use CSRF tokens for all state-changing forms.
- Use password hashing (`password_hash` / `password_verify`), session ID regeneration at login, secure cookie flags in production and inactivity timeout.
- No plaintext passwords, no default shared admin password, no public role self-selection.

# TECHNICAL ARCHITECTURE

## Required stack
- Apache through XAMPP.
- PHP 8.2+ style code (use features compatible with the PHP version actually bundled with the target XAMPP install; state the required PHP version in README after checking runtime).
- MySQL/MariaDB through XAMPP; use InnoDB, utf8mb4 and portable SQL.
- PDO for all DB operations with prepared statements.
- HTML5, CSS3, Bootstrap 5.x and vanilla JavaScript. Use local vendor assets where possible so the website is usable in a local/offline demo.
- Use one icon library consistently (Bootstrap Icons or Font Awesome Free).
- No Node/React/Next.js replacement. This is a PHP/MySQL XAMPP project unless the owner approves a stack change.

```text
├── public/ (index.php, .htaccess, assets/css, assets/js, assets/images, vendor)
├── routes/ (web.php)
├── storage/ (private_uploads, logs, exports, backups)  [deny direct web access]
├── tests/ (unit, feature, manual QA)
├── scripts/ (create-admin.php, backup.php, health-check.php)
├── .env.example
├── .gitignore
└── README.md
```

## Request lifecycle
Browser → Apache rewrite → `public/index.php` front controller → Router → middleware (session, CSRF, auth, role, permission) → controller → service/model via PDO → view/layout → response.

## Engineering rules
- Use a single front controller and route table; do not create dozens of duplicate unrelated PHP entry points.
- Keep SQL in models/repositories/services, not in templates.
- Use controllers for HTTP orchestration and services for business logic.
- Use reusable layouts and components; keep public and role portal shells separate but visually consistent.
- Validate server-side, escape output with `htmlspecialchars`, and use prepared SQL.
- Use POST/Redirect/GET after mutations; add CSRF tokens and transaction boundaries for multi-table operations.
- Use pagination and indexed queries for lists; do not load all cadets/results at once.
- Use transactions for admissions submit/approval, fee verification, result publishing, cadet account creation and attendance batches.
- Keep application config/credentials outside public document root; never commit real secrets.
- Use explicit timezone configuration (Asia/Karachi) and store timestamps consistently; display local Pakistan time.
- Create readable error pages and server logs; never show stack traces/database passwords in production.

## Asset handling
- Official logo is a user-supplied image; store it unchanged in `public/assets/images/brand/` and optionally create size-optimized copies while preserving original.
- Hero/campus photography must be verified/authorized; use placeholders until supplied.
- Uploads: store under `storage/private_uploads/` with random filenames and metadata in DB; serve through an authorized download controller, not direct path.
- Never allow PHP, script, HTML or executable files to be uploaded.

# SECURITY, PRIVACY AND DATA INTEGRITY REQUIREMENTS

- Passwords: `password_hash(PASSWORD_DEFAULT)` and `password_verify`; allow password rehash; no plaintext or reversible storage.
- Sessions: `session.use_strict_mode=1`, regenerate session ID after login/privilege changes, HttpOnly, SameSite=Lax/Strict, Secure in HTTPS production, idle timeout and full server-side logout.
- Authorization: server-side role + permission + ownership checks on every private request.
- SQL: PDO prepared statements only; no string-concatenated user input in SQL.
- XSS: escape output by context; sanitize rich text with a strict allowlist; do not execute uploaded/user-supplied markup.
- CSRF: token validation on every state-changing POST, including logout and AJAX mutations.
- Rate limiting: login, password reset, admission tracking and public form submissions. Avoid revealing whether an email/account exists.
- File upload: allow only required extensions and MIME/signature combinations (e.g. PDF/JPEG/PNG as configured); random names; max sizes; verify actual content; reject executable content; store outside public web root; scan if host supports it; log uploader and owner; download only after authorization.
- Admission deposit slip rule from supplied screenshot: PDF/JPG max 2 MB. If PNG is later allowed, get owner approval first.
- Alumni image: allow safe image types only; re-encode images if possible; enforce size and dimensions.
- Data minimization: CNIC, DOB, addresses, guardian phone, marks, fee/hostel records and deposit slips are private. Do not show in public directories or open search endpoints.
- Result search: rate-limit; require adequate identifiers; avoid incremental roll-number enumeration; show minimal public-safe data only after official publication.
- Audit: record actor, action, entity, entity ID, timestamp, IP/user agent where policy permits, and change summary for sensitive operations. Do not log passwords, session tokens or full sensitive documents.
- Database: enforce foreign keys, unique constraints and indexes; use transactions; soft-delete/archival for linked academic/financial records; protect backups.
- Production: HTTPS, least-privilege database account, secrets outside web root, debug off, setup route disabled, directory listing off, security headers and regular patching.
- Backup: encrypted where feasible, access restricted, rotation and documented restore test. Backup is not complete until restore is verified.
- Do not add live GPS tracking, biometrics, payment gateways or third-party sign-in without explicit college requirement and proper consent/configuration.

# XAMPP INSTALLATION, LOCAL RUN AND ONLINE DEPLOYMENT

## Local development
1. Install XAMPP and start Apache + MySQL from the XAMPP Control Panel.
2. Extract the generated source project into `C:\xampp\htdocs\brc-zhob\` (Windows default path).
3. Create database `brc_zhob_db` in phpMyAdmin, or use the project's installer.
4. Copy `.env.example` to the local config file described by the project README. Set DB host/name/user/password for the local XAMPP instance. Never commit real credentials.
5. Import `database/schema.sql` and role/permission seed data, or run the safe installer command.
6. Configure Apache document root to the project's `public/` directory using a local VirtualHost, or use the documented `http://localhost/brc-zhob/public/` fallback.
7. Run the one-time setup wizard to create the first Super Admin. It must require a strong unique password; no known default admin credentials.
8. Sign in as Admin, configure verified college content and test all roles using separate demo accounts.

## Example VirtualHost (optional, recommended)
```apache
<VirtualHost *:80>
    ServerName brc-zhob.local
    DocumentRoot "C:/xampp/htdocs/brc-zhob/public"

        AllowOverride All
        Require all granted
    </Directory>
</VirtualHost>
```
Add `127.0.0.1 brc-zhob.local` to the Windows hosts file (`C:\Windows\System32\drivers\etc\hosts`) and restart Apache. Then open `http://brc-zhob.local`.

# DATABASE MODEL NOTES

`schema.sql` is an initial normalized baseline, not a replacement for review. The coding agent must inspect it, add missing columns/tables needed for implemented routes, create migrations and test on the XAMPP MariaDB version. Never drop/overwrite user data during upgrades.

## Main relationship groups
- `roles → users`; `roles ↔ permissions` through `role_permissions`.
- `users → staff_profiles` for teachers/staff; `users → cadets` for student accounts; `users → parent_profiles`; `users → alumni_profiles` after approval.
- `cadets ↔ guardians` through `cadet_guardians`; parent authorization must verify this link.
- `academic_years → classes/subjects/exams`; `classes → sections`; `class_subjects` ties classes, subjects and academic years; `teacher_assignments` ties teachers to assigned class subjects.
- `attendance_sessions → attendance_records → cadets`.
- `assignments → assignment_submissions → cadets`.
- `exams → exam_subjects → exam_marks`; `exam_duties` assigns staff to examinations.
- `hostel_blocks → hostel_rooms → hostel_allocations → cadets`; `warden_remarks` has a visibility level.
- `fee_invoices → fee_invoice_items` and `fee_payments`; payments remain pending until a finance-authorized user verifies.
- `admission_applications → admission_documents / admission_fee_details / application_status_history`; conversion to `cadets` is a transactional one-time operation.
- `alumni_profiles ↔ alumni_contribution_types` through `alumni_contributions`.
- `notices → notice_attachments`; `gallery_albums → gallery_images`; `content_pages` and `site_settings` power public CMS.
- `notifications`, `messages`, `leave_applications`, and `audit_logs` support communications and accountability.

## Required additions during implementation
- Define a proper `exam_results`/report-card aggregation service with rules approved by BRC; marks table is raw input only.
- Add a timetable table set (e.g. `timetable_entries`) with unique period/room/teacher/class constraints.
- Add import/export job tables only if bulk import/export is implemented.
- Add file metadata/checksum/owner table if a unified upload registry is required.
- Consider encrypted fields or restricted access for sensitive CNIC/account/guardian details according to BRC policy.
- Add unique constraints only where the institution confirms uniqueness policy (e.g. parent emails may be shared by siblings).
- Add all foreign keys/indexes needed for the final queries; test migrations on MariaDB, not only MySQL.

## Database setup rules
- Use prepared statements and transactions.
- Do not use root DB credentials in production.

- Demo seed records, if supplied, must be clearly marked as fictional, removable and disabled from public output.
